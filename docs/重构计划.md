# EEGSpark 项目重构计划

## 当前问题

经过对项目结构的分析，我们发现以下几个主要问题：

1. **代码组织混乱**：相关功能的文件分散在不同目录
2. **修复工具分散**：Spark连接和Py4J修复相关的文件没有集中管理
3. **测试文件与源代码混合**：测试文件直接放在src目录下
4. **文档分散**：README和说明文档分布在不同位置
5. **缺乏明确的模块边界**：模块之间的依赖关系不清晰

## 详细重构方案

### 1. 文件移动计划

#### 创建新的工具目录

```
src/utils/
├── spark_fixes/
│   ├── __init__.py
│   ├── spark_connection_fix.py  (从 src/visualization/ 移动)

│   ├── fix_ivy_config.py        (从 src/ 移动)
```

#### 创建测试目录

```
tests/
├── __init__.py
├── unit/
│   ├── __init__.py
│   ├── test_ivy_config.py       (从 src/ 移动)
│   ├── test_py4j_connection.py  (从 src/ 移动)
│   ├── test_sparkcontext.py     (从 src/ 移动)
│   └── test_visualization_py4j_fix.py (从 src/ 移动)
├── integration/
│   └── __init__.py
```

#### 整理文档

docs/

#### 创建脚本目录

```
scripts/

### 2. 导入路径更新

在移动文件后，需要更新以下文件中的导入路径：

1. **src/visualization/spark_connection_fix.py**
   - 将 `from fix_ivy_config import fix_ivy_repository_path` 改为 
   - `from utils.spark_fixes.fix_ivy_config import fix_ivy_repository_path`

2. **src/main.py** 和其他引用了修复工具的文件
   - 更新所有引用了移动文件的导入语句

3. **测试文件**
   - 更新所有测试文件中的导入路径

创建统一的配置目录：

```

├── spark/
│   └── spark-defaults.conf

### 5. 实施步骤

1. **备份**：在开始重构前，创建项目的完整备份

2. **创建新目录结构**：
   ```
   mkdir -p src/utils/spark_fixes
   mkdir -p src/utils/logging
   mkdir -p tests/unit
   mkdir -p tests/integration
   mkdir -p docs/design
   mkdir -p docs/technical
   mkdir -p docs/modules/processor
   mkdir -p docs/modules/visualization
   mkdir -p scripts/setup
   mkdir -p scripts/docker
   mkdir -p config/spark
   mkdir -p config/docker
   mkdir -p config/logging
   ```

3. **移动文件**：按照上述计划移动文件

4. **更新导入路径**：修改所有受影响文件中的导入语句

5. **创建必要的 `__init__.py` 文件**：确保新创建的Python包目录都有 `__init__.py` 文件

6. **测试**：在每个主要步骤后进行测试，确保功能正常

7. **更新文档**：更新README和其他文档，反映新的项目结构

## 重构后的优势

1. **清晰的模块边界**：每个模块的职责更加明确
2. **简化的导入路径**：相关功能集中在一起，减少复杂的导入路径
3. **更好的可测试性**：测试与源代码分离，便于编写和运行测试
4. **文档集中管理**：所有文档集中在docs目录，便于查找和更新
5. **更好的可维护性**：结构清晰的代码更容易维护和扩展

## 注意事项

1. 重构过程中应该逐步进行，每完成一个小步骤就进行测试
2. 特别注意更新导入路径，确保所有引用都正确
3. 保持原有的功能不变，只改变代码的组织方式
4. 考虑使用版本控制系统（如Git）来跟踪变更，便于回滚

## 后续建议

1. **添加更多文档**：为每个模块添加详细的文档，说明其功能和用法
2. **增加单元测试**：提高代码的测试覆盖率
3. **标准化配置管理**：使用统一的配置管理方式
4. **考虑使用依赖注入**：减少模块间的直接依赖
5. **添加CI/CD流程**：自动化测试和部署过程
