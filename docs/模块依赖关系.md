# EEGSpark 项目模块依赖关系

## 模块概述

本文档描述了 EEGSpark 项目中各主要模块之间的依赖关系，帮助开发者理解代码结构和重构方向。

## 核心模块

### 1. 通用模块 (common)

- **eegrdd.py**: 定义 EEG 数据的 RDD 结构，被处理器和可视化模块使用
- **error_logger.py**: 错误日志记录工具，被所有模块使用
- **spark_context_manager.py**: Spark 上下文管理器，被处理器和可视化模块使用

### 2. 处理器模块 (processor)

- **eeg_processor.py**: 基础处理器类，被其他具体处理器继承
- **pipeline.py**: 处理流水线，协调多个处理器的执行
- **async_source_localization.py**: 异步源定位处理器
- **source_localization.py**: 源定位处理器
- **connectivity.py**: 连接性分析处理器
- **time_frequency.py**: 时频分析处理器
- **statistical.py**: 统计分析处理器

### 3. 接收器模块 (receiver)

- **receiver.py**: 数据接收器，接收来自发送器的数据

### 4. 发送器模块 (sender)

- **sender.py**: 数据发送器，发送数据到接收器
- **eeg_reader.py**: EEG 数据读取器，读取 EEG 数据文件

### 5. 可视化模块 (visualization)

- **visualizer.py**: 基础可视化器类，被其他具体可视化器继承
- **flask_server.py**: Flask Web 服务器，提供 Web 界面
- **api_server.py**: API 服务器，提供 RESTful API
- **websocket_server.py**: WebSocket 服务器，提供实时数据推送
- **spark_connection_fix.py**: Spark 连接修复工具

### 6. 修复工具 (分散在多个位置)

- **docker_py4j_fix.py**: Docker Py4J 修复工具
- **fix_ivy_config.py**: Ivy 配置修复工具

## 详细依赖关系

### 1. 处理器模块依赖

- **处理器模块** 依赖于 **通用模块** 中的 `eegrdd.py` 和 `spark_context_manager.py`
- **处理器模块** 中的具体处理器依赖于基础处理器类 `eeg_processor.py`
- **处理器模块** 中的 `pipeline.py` 依赖于各个具体处理器

### 2. 可视化模块依赖

- **可视化模块** 依赖于 **通用模块** 中的 `eegrdd.py` 和 `spark_context_manager.py`
- **可视化模块** 依赖于 **处理器模块** 的处理结果
- **可视化模块** 中的 `spark_connection_fix.py` 依赖于 `fix_ivy_config.py`
- **可视化模块** 中的具体可视化器依赖于基础可视化器类 `visualizer.py`

### 3. 修复工具依赖

- **修复工具** 之间存在相互依赖，如 `spark_connection_fix.py` 依赖 `fix_ivy_config.py`
- **修复工具** 被 **通用模块** 和 **可视化模块** 使用

## 重构建议

基于上述依赖关系，我们提出以下重构建议：

1. **集中修复工具**：将所有修复工具集中到 `src/utils/spark_fixes/` 目录下，减少跨模块依赖

2. **明确模块边界**：
   - 处理器模块应专注于数据处理逻辑
   - 可视化模块应专注于数据展示逻辑
   - 通用模块应提供被多个模块共享的功能

3. **减少循环依赖**：
   - 避免处理器模块和可视化模块之间的循环依赖
   - 通过接口或事件机制解耦模块间的直接依赖

4. **统一错误处理**：
   - 使用通用模块中的 `error_logger.py` 进行统一的错误处理
   - 避免在各模块中重复实现错误处理逻辑

## 结论

通过理解模块间的依赖关系，我们可以更有针对性地进行代码重构，使项目结构更加清晰，减少不必要的依赖，提高代码的可维护性和可扩展性。

重构应该遵循"高内聚，低耦合"的原则，确保每个模块都有明确的职责，且模块间的依赖关系简单清晰。
